# Design: a StartOS package for Lightning Addresses, NWC and NIP-05 on LND

Package id: `lightning-identity` (names the entity the design is organized around, avoids colliding with `lnd` in dependency graphs, reads cleanly as a marketplace title). Status: design proposal, 2026-10-20, revised 2026-10-21 after review. Sources reviewed at their current heads: `Start9-Community/bolt12-pay-startos` (v0.3.14 wrapper, 2026-10-19), `Alex71btc/lndk-pay` (app v0.3.14), `davotoula/brollyzapper` (0.1.23, 2026-10-15), `Start9Labs/lnd-startos` (0.21.4-beta:5), `Start9Labs/start-os` (container runtime), `lndk-org/lndk`.

## 0. Status (2026-10-21)

Milestone 1 is implemented in `~/repos/lightning-identity-startos` (also `docs/design.md` there): guard/core/edge in Go under `service/`, the StartOS package under `startos/`, one Dockerfile. What ships: multiple identities, LNURL-pay/Lightning Address with LUD-12/18/21, NIP-57 zap receipts, NIP-05, the embedded policy-locked khatru relay at `/relay`, receive-only NWC (get_info, get_balance, make_invoice, lookup_invoice, list_transactions, payment_received notifications, NIP-44 + NIP-04), the guard baking the receive credential with `time-before` (the `iprange` of the first draft is gone, §5.1), the admin UI, and the Set Primary Domain / Set Admin Password / Rebake Credentials actions. `go test ./...` passes, including `internal/e2e`, which runs all three processes against a fake LND through bake → LNURL zap callback → settlement → receipt on the relay → NWC request/response → relay ACL rejection. Not yet done: a real build (`go mod tidy`, `make`) and an install on the box; §10's remaining items are checked there. Milestone 2 (sending) is implemented as of 2026-10-21 (later the same day): the guard speaks gRPC to LND through vendored, buf-generated stubs, registers the `lightning-identity-guard` middleware, bakes the spend credential with the custom caveat only while the latch is on and the middleware is registered, prices `SendPaymentV2` via `DecodePayReq`, enforces per-payment and rolling 24-hour caps with reservations settled from the response intercepts, and fails closed on any other method; the `authorize-sending` StartOS action is the only path that enables sending or raises a cap, lowering and disabling are socket requests from the admin UI; core pays through the spend credential over REST with per-connection budgets as the soft layer, keeps a payment ledger, and NWC gains `pay_invoice`, outgoing `list_transactions`, budget-as-balance and `payment_sent`. `internal/e2e/sending_test.go` proves the nine properties in §12. Milestone 2b (identity balances, decided and implemented 2026-10-21): each identity is a virtual wallet with its own ledger balance — settled received plus operator adjustments minus sent and in-flight — enforced in core before any payment, reported as `get_balance` unconditionally (never narrowed by a connection's budget), credited and debited from the admin UI; `ChannelBalance` left the receive credential, so no NWC client can learn the node's. Still untested on a real box; milestone 3 (BOLT12) is unstarted.

## 1. Recommendation in one paragraph

Build a new, small Go service with a four-process trust topology inside one StartOS package: a **public edge** (LNURL + NIP-05 + an embedded, policy-locked Nostr relay) that holds no credentials at all; a **core** (invoices, zap receipts, NWC, identities, admin UI) that holds only two narrowly baked, short-lived macaroons; a **guard** that is the only process with `admin.macaroon`, bakes those two credentials, and enforces hard spend caps *inside LND's request path* via the RPC middleware; and later an optional **LNDK** subcontainer for BOLT12. Every identity owns its own keys: a zap-signing key and an NWC service key, so relay ACLs, NWC info events and budgets attribute cleanly per identity. Borrow brollyzapper's design (its guard/server split, URI-scoped credentials, middleware cap) rather than its code or its single-identity shape — §9 records how that played out. Do not wrap `bolt12-pay` — the wrapper's topology cannot fix problems that live in the upstream process, and the wrapper itself mounts more of LND than it should (details in §2).

## 2. Why not just run bolt12-pay-startos

These were read from the source in October 2026, when the choice was made. The package has moved since; what changed is noted where it matters and summed up at the end of this section.

**2.1 The public process holds spend authority.** `start.sh` exports `LND_MACAROON_PATH=/mnt/lnd/data/chain/bitcoin/mainnet/admin.macaroon` and the FastAPI app reads it for every REST call it makes. The same process on the same port serves `/.well-known/lnurlp/*` to the internet and `/api/pay-bolt11`, `/api/pay-keysend`, `/api/pay-offer` to anyone holding a session cookie. `lndk` runs beside it with the same admin macaroon. One auth bypass, deserialization bug or SSRF in a 9,300-line `app.py` is a drained node.

**2.2 The wrapper mounted LND's entire `main` volume into that process (since fixed).** At the time, the wrapper mounted LND's whole data volume read-only, and in `lnd-startos` that volume's root held the wallet password and seed alongside `tls.key`, `wallet.db` and `channel.backup`. A bug that only let an attacker read a file, a far lower bar than code execution, would have been enough to take the seed. This was the single strongest reason not to ship that wrapper as it was. It has been fixed at its root: since 0.21.6-beta:2, lnd-startos exports credentials for dependents on a separate `public` volume and tells them never to mount `main` (§14), and the wrapper now mounts only the `admin` tier of it (checked 2026-11-18).

**2.3 An authentication gap (specifics withheld).** Reading the source turned up an API route that answers without a session. The specifics are deliberately not in this document: they belong in a private report to the maintainer, not in a public repository. The argument here does not need them. In a single process that both serves the internet and holds the node's credential, every route is one missing check away from being public, and the only durable protection is for the public process to hold nothing worth reaching.

**2.4 Admin and public share one interface.** The StartOS package exports one `ui` interface on 8081, `masked: false`. The address you must make public for Lightning Address resolution is the same address that serves the admin SPA and its login form. Cookie auth with lockout is the only barrier. There is no second host to bind a LAN-only admin to without changing upstream routing.

**2.5 Smaller things that add up.** `LND_REST_INSECURE=true` disables TLS verification to LND's REST (over the internal bridge, so lower impact). Upstream is pinned as a submodule commit, not a release. No spend caps of any kind. `lndk` is not health-checked. BOLT12 is bundled whether you want it or not, with the LNDK permission set (custom messages, node-announcement updates, shared-key derivation) carried by the admin macaroon anyway.

What a wrapper *could* fix: 2.2 (subpath mount), partially 2.4 (a reverse-proxy subcontainer in front that only forwards the public paths on the public interface, like brollyzapper's `PROXY_AUTH_WHITELIST`). What it cannot fix without forking upstream: 2.1 and 2.3, which is the core of your concern.

*Where it stands now (2026-11-18).* BOLT12 Pay has grown since this was written: beside Lightning Addresses and BOLT12 it now offers NIP-05 names, zap receipts and Nostr Wallet Connect, so the two packages overlap in features far more than they did, and it remains the only way to BOLT12 on LND under StartOS (§8). 2.2 is fixed. 2.1 and 2.4 are unchanged: one process, one interface, the admin macaroon, and limits enforced in the application. So the case for this package is no longer the feature list; it is the trust model, a wallet of its own for each identity, and a relay that is part of the service.

## 3. What brollyzapper gets right, and why forking it whole is the wrong shape

Right: the two-container split with a **guard** that alone mounts `admin.macaroon` (and only the two files, never the LND directory — its compose comments call out exactly the `wallet.db` hazard above); URI-scoped macaroons (`uri:/lnrpc.Lightning/AddInvoice`, not `invoices:write`, which covers every invoice-mutating RPC); `time-before` expiry with hourly renewal; a spend macaroon carrying an `lnd-custom brollyguard <nonce>` caveat so that LND routes every `SendPaymentV2` through the guard's registered RPC middleware, which enforces a rolling 24-hour cap and a per-payment cap *before* LND executes — a compromised server can lower its own caps but never raise them; receive-only by default with a ceremony to enable sending; and NWC with revocation-not-deletion. `lnd-startos` already forces `rpcmiddleware.enable=true` in `lnd.conf`, so this works unchanged on StartOS.

Wrong shape for us: one address name, one Nostr identity, one zap-signing key. That assumption runs through `internal/store` (3.6k LOC), `internal/wallet` (append-only balance ledger), `internal/api` (5k), `internal/web`, and the settings model, and it is enforced by ~60k lines of tests including an architecture test suite (`internal/arch`) that pins package boundaries, logger construction, secret-type usage and more. Making it multi-identity is a refactor of nearly every package against tests written for the old model; the resulting fork could never track upstream. It also has no NIP-05, no relay, no BOLT12 path, and pins a fork of `nbd-wtf/go-nostr` by commit, while an embeddable relay (khatru) now lives in the `fiatjaf.com/nostr` module.

So: **take the shape of its ideas, not its code.** The original plan was to vendor `internal/guard` + `internal/lnd` and `internal/nwc`; in the event everything was written fresh and smaller (see §9), with the ideas kept — public-route whitelist, URI-scoped credentials, hourly renewal, revoke-don't-delete, the middleware cap for milestone 2 — and the arch-test harness left behind.

## 4. Target architecture

One StartOS package, one LXC container, four subcontainers (three in v1). Everything below is a plain process; StartOS subcontainers are `unshare(CLONE_NEWNS)` + `pivot_root` with their own PID 1, share the package's **network namespace** (one IP, one loopback), and each daemon can run as its own `user` (SDK `Daemons.addDaemon({ exec: { user } })`). Isolation is therefore **mounts + uid**, not the network. Two consequences drive the design: a file not mounted into a subcontainer is unreadable from it, and loopback TCP is reachable from every subcontainer, so inter-process links use unix sockets in per-pair mounted directories with `SO_PEERCRED` uid checks, never loopback TCP.

| Subcontainer | uid | Listens on | Holds | Talks to |
|---|---|---|---|---|
| `edge` | `edge` | `:8080` public HTTP (+ `/relay` WebSocket) | nothing secret: identity table (ro), relay event store | `core` via `run/edge-core.sock` |
| `core` | `core` | `:8081` admin UI (LAN/Tor interface only); unix sockets | recv + spend macaroons (ro, baked by guard), per-identity zap-signing keys, NWC service keys, SQLite | LND gRPC over the bridge; guard socket; external relays (outbound); embedded relay over loopback WS |
| `guard` | `guard` (started as root, drops after reading `admin.macaroon` — see §10.2) | `run/guard.sock` only, no TCP | `admin.macaroon` (in memory; ro subpath mount), StartOS root CA, cap state | LND gRPC (bake, middleware stream) |
| `lndk` (milestone 3) | `lndk` | loopback gRPC `:7000` | its own baked macaroon | LND gRPC |

Trust boundaries, from most to least exposed: `edge` is reachable by the whole internet and can at worst spam invoices (bounded by rate limits and by the fact that it cannot call LND at all; it asks `core` for an invoice over a socket with a fixed schema). `core` is reachable from the LAN/Tor admin interface and from Nostr relays it chose to connect to; if fully compromised it can create invoices, read the invoices/payments it is scoped to, and spend up to the guard's caps and no further. `guard` has no listener; its only input is a unix socket mounted into `core` and a state directory that only the StartOS runtime (package JS, running actions) writes. The wallet seed is never mounted anywhere in this package.

### 4.1 Mounts

All on the package's `main` volume via `subpath`, so one volume is backed up but each process sees only its slice.

| Subpath | edge | core | guard | Purpose |
|---|---|---|---|---|
| `edge/` | rw | – | – | relay event store (SQLite), nothing else |
| `core/` | – | rw | – | SQLite (identities, NWC connections, pending zaps, ledger), encrypted key file |
| `identities/` | ro | rw | – | `identities.json` + `nwc-clients.json`, written by core, read by edge for LNURL metadata, NIP-05 and relay author allow-lists |
| `run/` | rw | rw | rw | unix sockets only (`edge-core.sock` 0660 edge:core, `guard.sock` 0660 core:guard); each daemon checks peer uid; the edge→core protocol is pinned in §4.3 |
| `credentials/` | – | ro | rw | `recv.macaroon`, `spend.macaroon`, `lnd-ca.pem` |
| `guard/` | – | – | rw | `state.json` (latch, caps, nonce), `authorization.json` written by the StartOS action |
| LND `public` volume, subpath `admin` (since 2026-11-10; before that LND `main`, subpath `data/chain/bitcoin/mainnet`) | – | – | ro at `/lnd/admin` | `admin.macaroon` and a copy of `tls.cert` only — LND's `main` volume is not mounted at all |

TLS to LND: `lnd-startos` issues `tls.cert` with `sdk.getSslCertificate`, so the chain ends in the StartOS root CA, and obtaining that root from our own package is already proven code — `openclaw-startos` does `sdk.getSslCertificate(effects, ['127.0.0.1']).const()` and takes `certs.slice(-1)` (the hostname is immaterial, only the root is wanted) in its `install-root-ca` oneshot. Where our package differs is what it does with the root: openclaw appends it to the system trust store with `update-ca-certificates` because Node, curl and `start-cli` consult that store; our guard and core are static Go binaries in distroless images with no `update-ca-certificates` and no need for the Mozilla bundle, so the package JS writes the root to `credentials/lnd-ca.pem` at init and both processes **pin** their LND dial to that single CA (`tls.Config{RootCAs: <that pool>}`). Pinning is strictly better than the system store here: a CA from the public bundle can never validate a man-in-the-middle of the LND leg. LND's gRPC leg is TLS passthrough (`secure: { ssl: true }`, no `addSsl`, because an OS rewrap negotiates no ALPN and gRPC-go rejects that), so the leaf we see is LND's own. `getBridgeAddress` resolves to `10.0.3.1:<per-service port>` — the OS's address on the LXC bridge, which is also what `effects.getOsIp()` returns (the SDK's own fallback path builds `<osIp>:<fallbackPort>`). `lnd-startos`'s `writeCerts` puts exactly that in the SAN list on purpose (`hostnames = [containerIp, '127.0.0.1', await sdk.getOsIp(effects), ...served]`, under the comment "gRPC is TLS passthrough, so every address a client dials has to be a SAN"), and bolt12-pay's working gRPC leg through the bridge is the empirical confirmation. So: dial `10.0.3.1:<port>`, verify against the pinned StartOS root, SAN `10.0.3.1` matches, done. Nothing from LND's volume root is mounted anywhere.

### 4.2 Interfaces

| Id | Type | Port | Served by | Exposure |
|---|---|---|---|---|
| `public` | `api` | 8080 | edge | the only interface you add a public domain to. StartOS terminates TLS (Let's Encrypt) and forwards HTTP. Paths: `/.well-known/lnurlp/{name}`, `/lnurlp/{name}/callback`, `/lnurlp/{name}/verify/{hash}` (LUD-21), `/.well-known/nostr.json`, `/relay` (WebSocket upgrade, NIP-11 on `Accept: application/nostr+json`), `/health`. Everything else 404, or the optional static site (§4.5). |
| `admin` | `ui` | 8081 | core | LAN/Tor only by convention; password-protected (package-generated, `set-password` action like openclaw-startos). Never give it a domain; the package docs and a `preferredLauncherAddress` steer the launcher to `.local`. |

Keeping the relay on the same port/path as the public API means one domain, one certificate, one firewall rule, and an NWC URI of `nostr+walletconnect://<svc-pubkey>?relay=wss://pay.example.com/relay&secret=…&lud16=name@pay.example.com`.

Client IP: a `protocol: 'http'` binding gets `addXForwardedHeaders: true` by default (start-core `knownProtocols`), and `AddSslOptions` documents it as "the OS reverse proxy adds `X-Forwarded-Proto: https` and `X-Forwarded-For: <client-ip>` … implies HTTP-aware proxying". So the edge does see the client IP for domain traffic. It must only *trust* the rightmost `X-Forwarded-For` value, since a LAN host can reach the bridge port directly and write the header itself; the worst that spoofing buys is a LAN host evading its own per-IP limit, so per-IP limits stay a second layer behind the per-identity and global buckets. WebSocket through that proxy is confirmed in practice: Lundog's box runs a Let's Encrypt domain over StartTunnel and LNbits's Nostr relay WebSockets work through it, so `/relay` on the same binding is fine.

**Abuse limits on the public interface (2026-11-11).** The first day the landing page was live, one address ran a vulnerability scan against it: about 150 requests in 27 seconds for `/.env`, `/.git/config`, lock files and framework debug routes. Every probe got a 404 in under a millisecond and nothing was exposed — the edge holds no credentials and serves only the `site` folder and the address endpoints — but none of it was rate limited either, because the per-client bucket was 120 a minute with a burst of 240. Four changes:

- *Scanner block.* What marks a scanner is not speed but that nearly every answer is "not found". The edge counts 404 and 405 answers per client; more than 20 in a minute and the client is refused everything (429 with `Retry-After`) for 10 minutes. The block is logged once when it starts and once when it ends, with the number of requests refused, instead of a line per request. Only public addresses can be blocked: if the client address is ever a private one (a proxy in front that drops the real address, an overlay network) then all visitors share it, and blocking it would take the public interface down for ten minutes on one scanner's account; those are rate limited only. The cost accepted: people behind the same public address as a scanner (CGNAT) are locked out with it for those ten minutes.
- *General limit.* 60 a minute with a burst of 60, down from 120/240. A landing page is about seven requests and paying a Lightning Address two or three. A zap service that fetches invoices for many users from one address could reach it; `EDGE_REQUESTS_PER_MINUTE` raises it. Refusals are logged at most once a minute per client.
- *Keys.* Limits are keyed on the IPv4 address or the IPv6 /64, since one IPv6 subscriber can rotate through a whole /64. A request with no `X-Forwarded-For` from loopback is core talking to the embedded relay and is exempt; a forwarded request cannot pass for one, because the OS proxy adds the header to everything from outside.
- *Less to read, less to reach.* The site and the default page answer GET and HEAD only (a file server answers POST with the file, which is how the scanner's `POST /` came back 200). `/health` returns only `{"ok":true}` or a 503 `{"ok":false}`; it used to report the identity count and uptime to anyone, and each hit was an IPC call into core and from there a `GetInfo` on LND — a public URL that reached LND once per request. The answer is now cached for 10 seconds, with concurrent callers waiting on one call. The default page no longer states how many identities are configured.

### 4.3 The edge→core socket: the one internet-reachable path into the privileged side

Everything the public internet can make `core` do passes through `run/edge-core.sock`, so the protocol is small, typed and bounded, and `core` treats `edge` as untrusted (it re-validates everything; a compromised edge must gain nothing beyond what an honest edge could request). Framing: length-prefixed JSON, hard frame cap 8 KiB, at most 32 requests in flight per connection, one connection per edge process, 5 s per-request timeout. Exactly three request types:

| Request | Fields and bounds | Core-side checks beyond schema |
|---|---|---|
| `create_invoice` | `identity_id` (must exist and be enabled), `amount_msat` (u64), `description_hash` (32 bytes hex), `comment` (≤ identity `commentAllowed`, ≤ 1 KiB), `zap_request` (optional, serialized kind-9734 ≤ 4 KiB), `payer_data` (optional, ≤ 1 KiB) | amount within the identity's min/max; description hash recomputed from the identity's own metadata (never trusted from edge); zap request re-parsed and signature-verified per NIP-57 Appendix D, `amount` tag must equal `amount_msat`; per-identity and global invoice-rate caps enforced here independently of the edge's limiter; unsettled-invoice ceiling per identity |
| `verify_invoice` | `payment_hash` (32 bytes hex) | LUD-21 answer only for hashes this package created; preimage returned only once settled |
| `status` | none | returns the one boolean `/health` needs (core can reach LND); nothing operator-identifying. The edge asks at most once every 10 s (§4.2, abuse limits) |

This is the only injection point from the internet into a process that holds credentials, and `create_invoice` is the only one with attacker-chosen content, so its bounds are the ones to fuzz in CI. There is deliberately no generic "query" or "admin" message on this socket; the admin UI reaches core by its own listener on the admin interface.

### 4.4 Package surface (actions, tasks, health, backups)

Actions: `set-primary-domain` (the bolt12-pay pattern — pick one of the `public` interface's non-local addresses; drives the `lud16` domain, NIP-05 domain and relay URL); `set-admin-password`; `enable-sending` / `raise-caps` (the authorization ceremony, §5.3); `rebake-credentials` (forces the guard to re-bake now, e.g. after LND's `revoke-macaroons`); `rotate-master-key` (§7.1); `show-status` (guard view: wallet state, credential expiry, caps, middleware registered or not).

Tasks: `set-primary-domain` and `set-admin-password` both raised `critical` (shown as Required, gating start) at install and until done; the domain task comes back if the chosen domain disappears. (The first draft copied bolt12-pay's `critical`-only-on-loss; that package still runs without a domain, this one has nothing to do without one — changed 2026-10-21 after the first install showed it as merely Recommended.)

Health: `edge` — `/health` 200 `{"ok":true}` (503 `{"ok":false}` when core or LND does not answer) and relay NIP-11 answers; `core` — socket up and LND `GetInfo` through the recv macaroon succeeds; `guard` — credentials present, >1h from expiry, middleware registered (the guard reports this on its socket; if the middleware is down the spend macaroon is *dead*, not unrestricted, because LND rejects a custom caveat with no middleware registered — brollyzapper verified this and we inherit it).

Dependency: `lnd` required, `kind: 'running'`, `healthChecks: ['lnd']`, `versionRange >= 0.21.x` (so onion messages exist for milestone 3). LND addresses resolved with `sdk.host.getBridgeAddress` exactly as bolt12-pay does; omitted until LND binds, `.const()` heals with one restart.

Backups: `sdk.Backups.ofVolumes('main')` minus `credentials/` (re-baked) and `run/`. `guard/state.json` *is* backed up (caps and latch are operator decisions), and so is `core/` including the master key (§7.1), so a restore brings identities, zap keys and every NWC pairing back intact; nothing in `core/` is tied to a particular LND node, so a restore onto a different node needs only `rebake-credentials`. An uninstall revokes nothing (brollyzapper's OPERATING.md point; the remedy is LND's own `revoke-macaroons` action).

### 4.5 Domain layout: root vs subdomain, and where each address type actually resolves

The three address types resolve in two different places, and that is what decides the layout. Lightning Address (LUD-16) and NIP-05 are both HTTPS: `alias@host` means `GET https://host/.well-known/lnurlp/alias` and `GET https://host/.well-known/nostr.json?name=alias` respectively, so the host after the `@` must be the host whose HTTPS the `public` interface serves — root or subdomain, the package does not care, and both address types live at whatever host that is. BIP-353 is DNS only: `alias@domain` means a DNSSEC-signed TXT record at `alias.user._bitcoin-payment.domain`, no HTTP involved, so a BIP-353 address can sit at the bare root (`alias@yourdomain.com`) regardless of which host serves HTTPS. That is exactly why lndk-pay's "dedicated LNURL subdomain" example keeps `bolt12@yourdomain.com` while LNURL moves to `pay.yourdomain.com`.

On StartOS a domain is assigned to one interface of one package, with no path-based splitting across packages, so "root domain for addresses *and* a website on the root hosted elsewhere" is not possible as such. Two layouts cover the real cases:

| | HTTPS host bound to `public` | Lightning Address | NIP-05 | BIP-353 (DNS) | Website |
|---|---|---|---|---|---|
| **Subdomain** | `ln.yourdomain.com` | `alias@ln.yourdomain.com` | `alias@ln.yourdomain.com` | `alias@yourdomain.com` | root stays free for anything |
| **Root** | `yourdomain.com` | `alias@yourdomain.com` | `alias@yourdomain.com` (and `_@yourdomain.com`, which clients display as just the domain) | `alias@yourdomain.com` | served by `edge` as static files (below), or none |

To make the root layout viable without giving up a site, `edge` serves an optional **static site** from `main/site/` at `/` (everything not matched by the well-known, `/lnurlp/`, `/relay` and `/health` routes): plain files, no templating, no uploads through the public interface, `index.html` fallback, cache headers — a feature that costs nothing in attack surface because `edge` already holds no secrets and already is a static-content server for the LNURL and NIP-05 documents. A dynamic site cannot live there; for that case use the subdomain layout.

**Managing the site's files (2026-11-17).** Until now the only way to fill `site/` was a file manager or SSH on the box, which not every operator has. Two StartOS actions replace that: **Upload Site** takes one zip archive and **Remove Site** empties the folder. An action was chosen over a file manager in the Admin UI because of where the work happens. StartOS authenticates the operator, receives the bytes, enforces the size limit and writes the file; neither daemon parses an upload, and core — the process with the keys and the LND credential — still has no access to `site/` at all, where an Admin UI page would have needed write access to a folder the public side serves. The price is the floor: action file uploads arrived in StartOS 0.4.2 (start-sdk 4.1.0, merged upstream 2026-11-07 and tested there with mocks only), so the package now requires it.

How it is put together:
- *The archive never lands in `site/`.* Everything there is served, so an archive uploaded there would be downloadable until it was unpacked. It goes to `upload/`, which no daemon mounts, under a random name per form, and is deleted when the action ends whether or not it worked. Archives nobody came back for are swept after two hours (when a form is opened and at service start).
- *The unpacker is ours and small* (`service/internal/site`, Go's standard `archive/zip`), not busybox `unzip`, so that every rule is exact and unit-tested, including by removing each check and seeing a test fail. It runs once as `edge site install` in a throwaway container that mounts `upload/` read-only and `site/` and nothing else. It is in the edge binary because that is the one that links no credential code.
- *The archive is treated as hostile.* A name that is absolute, climbs out with `..` (with either slash), has a control character or is not UTF-8 refuses the whole archive, as does a path that is both a file and a folder, a password-protected archive, more than 2,000 files or more than 200 MB — the last measured as bytes are written, not read from the headers. Only regular files and folders are ever created; links and special files are left out and counted. Permissions are set explicitly (0644, 0755) whatever the umask.
- *Hidden files are left out.* The folder an operator zips is often a project folder, and `.git` and `.env` are exactly what scanners ask for. Anything with a segment starting with a dot is skipped, with one exception, a top-level `.well-known` (for `security.txt`). Edge applies the same rule at request time, so it also covers files put there by hand and the installer's own work folders.
- *Archives as people make them.* Finder and Explorer wrap everything in the folder that was compressed and add `__MACOSX`, `.DS_Store`, `Thumbs.db`. One wrapping folder is dropped from the paths when the index is inside it; the clutter is skipped; backslashes are read as separators. A path listed twice was refused at first, as something no honest tool does; the first real archive showed otherwise (2026-11-18: Finder writes a file twice when a folder and the files inside it are both selected before Compress). The later entry now stands, as with `unzip`, and is unpacked and counted once.
- *Replace by default, keep as an option.* The archive is unpacked and checked in `site/.incoming` first (same mount, so the final step is renames; hidden, so never served). Replace moves the old entries to `site/.outgoing`, moves the new ones in, then deletes the old: a refused archive changes nothing, and the site is a mixture of old and new only for as long as the renames take. Keep moves each new file over its path and removes nothing; where a folder is needed and something else stands (a file, or a link put there by hand) it is replaced by a real folder, so nothing is written through a link.
- *No restart.* Edge used to decide at startup whether a site existed. It now checks for `index.html` on each request (one `stat`), because restarting to notice would drop every wallet's relay connection.

Not done, deliberately: `.tar.gz` (one format is one code path to secure, and every desktop makes a zip); a file listing or per-file delete (the archive is the unit; replace is the edit); a download of the current site, which the same StartOS release makes possible and can be added if it is missed.

Two partial hybrids exist and are documented as such, not recommended: a website host on the root can serve NIP-05 statically (`nostr.json` is just a file; `core` can export it from the admin UI) so NIP-05 reads `alias@yourdomain.com` while Lightning Addresses stay on `ln.`; and a root host can even serve a static `/.well-known/lnurlp/alias` whose `callback` points at `https://ln.yourdomain.com/lnurlp/alias/callback` (LUD-06 allows any callback URL). Both reintroduce the "static file to keep in sync" problem the design otherwise avoids, so the admin UI should show a staleness warning if it ever offers the export.

## 5. Credentials and the guard

### 5.1 Macaroon sets (URI-scoped, baked with `BakeMacaroon`)

Receive (`core`, always): `/lnrpc.Lightning/GetInfo`, `/lnrpc.Lightning/AddInvoice`, `/lnrpc.Lightning/LookupInvoice`, `/lnrpc.Lightning/SubscribeInvoices`, and since 2026-10-21 `/invoicesrpc.Invoices/CancelInvoice` for self-pay (§6.5; cancel-only, it can settle or create nothing — a compromised core could cancel the node's other open invoices, which is a nuisance, not a loss). Otherwise that is all: no `ListInvoices`/`ListPayments` (brollyzapper omits them too and serves history from its own ledger; `list_transactions` is built from core's ledger, which is also what makes it per-identity) and, since 2026-10-21, no `ChannelBalance` either — balances are per-identity ledger positions (§6.3), so the credential that the internet-facing half of the service holds cannot reveal the node's liquidity. Fewer URIs is better.

Spend (`core`, milestone 2, only after the ceremony): `/routerrpc.Router/SendPaymentV2`, `/routerrpc.Router/TrackPaymentV2`, `/lnrpc.Lightning/DecodePayReq`, with the custom caveat `lnd-custom lightning-identity-guard <nonce>`.

LNDK (milestone 3): the set from LNDK's README — `GetInfo`, `ListPeers`, `SubscribePeerEvents`, `SendCustomMessage`, `SubscribeCustomMessages`, `/peersrpc.Peers/UpdateNodeAnnouncement`, `/signrpc.Signer/DeriveSharedKey`, `/verrpc.Versioner/GetVersion`; and for paying offers the additional `/walletrpc.WalletKit/DeriveKey`, `/signrpc.Signer/SignMessage`, `GetNodeInfo`, `ConnectPeer`, `GetChanInfo`, `QueryRoutes`, `/routerrpc.Router/SendToRouteV2`, `TrackPaymentV2`. A precision point on how the cap works: LND forwards *every* request whose macaroon carries the custom caveat to the registered middleware, whatever the method, so the mechanism itself can cap anything. What is method-specific is the guard's *pricing logic*, which brollyzapper wrote for `SendPaymentV2` only (it decodes the bolt11 to learn the amount). LNDK pays offers with `SendToRouteV2`, whose amount lives in the route, not in an invoice; the vendored guard would let that through uncapped unless we add a `SendToRouteV2` pricer that sums the route's `total_amt_msat`. Until that exists, BOLT12 in milestone 3 is receive-only, and the LNDK macaroon simply omits the paying URIs.

Every credential carries `time-before` (24h) and is renewed hourly by the guard.

IP caveats, precisely: an IP lock separates nothing *inside the box*, and it does bound a credential that leaves it. Inside the package, every subcontainer shares one network namespace, so edge and core present the same address. Between packages the same holds for a less obvious reason: StartOS's `forward-port` script installs `postrouting ip saddr <bridge-subnet> ip daddr <target> … masquerade` for every bridge forward, so a container dialing another container through `10.0.3.1:<port>` is masqueraded and LND sees the source as `10.0.3.1` — every service on the box looks identical to LND, and a compromised neighbour package would pass an `ipaddr 10.0.3.1` check. A LAN client is different: its forward is DNAT without masquerade, so LND sees the real LAN address, and lnd-startos exposes gRPC on the LAN (`.local`) and Tor by default. That is the case an IP caveat closes: a macaroon that leaked through a backup, a log line or an admin-UI bug cannot be used from a laptop on the LAN, only from inside the box, on top of the 24-hour expiry. So the guard bakes `iprange 10.0.3.0/24` (the bridge subnet, derived from `getOsIp()`/`getContainerIp()` at init, `iprange` rather than `ipaddr` so it holds whether a path is masqueraded or direct) onto both credentials, and the code comment says exactly what it does and does not do, so nobody mistakes it for isolation between edge and core. The known failure mode is brollyzapper's: a wrong subnet fails closed and looks like a bake failure, so the guard's status reports the caveat values it baked.

**Withdrawn on the box, 2026-10-21.** The very first bake failed its probe with `caveat "iprange 10.0.3.0/24" not satisfied: macaroon locked to different IP range`, and the reason is in lnd-startos: its REST interface is bound with `addSsl`, so the OS's TLS proxy terminates the connection and opens its own to LND's plain REST port. LND sees the proxy as the client of every REST call — ours, another package's, a LAN laptop's — and an IP caveat on a REST-used credential cannot distinguish any of them; the analysis above holds only for gRPC, which is passthrough (the guard's middleware registration over gRPC succeeded on the same box). So the package sets no `GUARD_IPRANGE` and both credentials carry `time-before` only, plus the custom caveat on the spend one; the 24-hour expiry and URI scoping are what bound a leak. The guard keeps the option, and it becomes worth switching on if core's LND client ever moves from REST to gRPC (the stubs and `lndgrpc.Dial` already exist; AddInvoice, LookupInvoice, SubscribeInvoices, DecodePayReq, SendPaymentV2 and the guard's bake would move) — a decision for after the milestones are proven on the node, not before.

### 5.2 Hard caps in LND's request path

The guard registers an RPC middleware (`RegisterRPCMiddleware`, custom caveat name `lightning-identity-guard`, `readOnly: false`). LND then routes every request bearing that caveat to the guard; for `SendPaymentV2` the guard decodes the invoice amount, checks it against the per-payment cap and the rolling 24-hour window (persisted in `guard/state.json`), and either passes the request through or replaces it with a rejection; any method the guard has no pricer for and that is not on an explicit read-only allow-list (`TrackPaymentV2`, `DecodePayReq`) is rejected, so adding a URI to the spend macaroon without adding a pricer fails closed. Caps are enforced even if `core` is fully compromised, which is the property the LNbits/bolt12-pay single-process model cannot offer. Core additionally keeps per-connection NWC budgets (soft limits, per identity) so ordinary misuse is caught before the guard ever sees it.

**Liquidity view (2026-11-12).** Identity balances are a ledger (§6.3) and nothing in core could say whether the node can pay them out or whether a payment has room to arrive; the dashboard only carried a sentence telling the operator to keep outbound liquidity above the total. Core is still not given a channel permission. Instead the guard, which holds the admin macaroon anyway, reads `ListChannels` at most every 30 s (a failed read is cached as long, and concurrent status requests share one call) and adds a summary to the *reply* to core's `status` request — not to `status.json`: per channel, the peer's alias and node key, online or not, announced or not, and what each side can move, taken as balance minus that side's channel reserve, floored at zero; totals over online channels; the largest single channel each way; what offline channels would add; the amount in in-flight HTLCs. Sums saturate rather than wrap. The alias has to be asked for (`peer_alias_lookup=true`; LND leaves it empty by default, which is why the first build showed only keys), is free text set by the other node's operator, and comes back as an error sentence when LND has none on record: the guard drops that sentence, strips control characters and cuts it to 32 characters, and the page shows the alias with the shortened key beside it, or the key alone. Routing fees, HTLC limits and commitment fees beyond what LND already nets out are not modelled, so the figures are approximate. The Admin UI shows the two totals, the channel rows (a line for in-flight HTLCs only when there are any), and warnings for: no channels, every channel offline, nothing receivable, some channels offline, and identity balances exceeding what can be sent (with the shortfall). The e2e test proves core's receive credential is refused the channel list by the node and that twenty status requests cost one LND read. What this widens: core now learns the node's liquidity and peer aliases, over the guard socket, for the operator's page only; NWC `get_balance` is unchanged and nothing public reads it. The card first carried a sentence under the totals explaining how they are worked out and, with several channels, the largest single payment each way; it was removed the same day as wordy next to the channel rows that already show it. The guard still reports the largest-channel figures; the page does not use them.

**Admin UI layout, and confirmations that never ran (2026-11-18).** The dashboard had grown in the order things were built: node, guard, liquidity, sending, settings, domain, and the identities last. It now leads with the identities, which is what an operator opens the page for, and the node, the guard and the credentials (expiry, allowed RPCs, caveats, whether the caps check is registered) moved to a **System** page. Moving them must not hide a fault, so the dashboard computes a list of what is wrong — guard not answering, its last error, no receive credential, sending enabled without its middleware or its credential, LND unreachable or unsynced — and shows it in a box until it clears. Each identity is linked once, by its name; every page below the dashboard has a way back; and a result can be put away, which matters most for a new NWC connection string, which used to stay on the page until the operator navigated elsewhere.

Doing that work turned up a real bug. The pages' content security policy is `default-src 'none'` with no `script-src`, which blocks inline event handlers, and the destructive forms relied on `onsubmit="return confirm(...)"`. A browser never ran them: "Delete identity", "Rotate wallet key" (which revokes every connection) and "Disable sending" acted on a single click, confirmed in a headless browser against the running handler. The fix keeps the policy and removes the script: such a button is a `<details>` element whose summary is the button and whose body says what will happen and holds the real submit, and a result is dismissed by a link to the same page (it is shown once, so reloading puts it away). Revoking a connection asks the same way. A test now fails if any page contains a script or an inline handler.

**Admin UI icon (2026-11-12).** The header and the favicon use the package icon, served unauthenticated at `/icon.svg` (and `/favicon.ico`) with a day's caching, since the login page shows it too. `go:embed` cannot reach above the module, so `service/internal/admin/static/icon.svg` is a copy of the root `icon.svg`; a test fails when they differ.

### 5.3 The authorization ceremony, StartOS-native

brollyzapper makes the operator fetch a one-time code from a file in Umbrel's Files app because an Umbrel app has no other out-of-band channel. StartOS has one: **actions**. The package's `enable-sending` / `raise-caps` actions run in the StartOS runtime, outside every HTTP surface, and can write into `guard/` (a subpath only the guard mounts) with `sdk.volumes.main.subpath('guard/authorization.json')`. The flow: the operator clicks the action in the StartOS UI, confirms the new caps in the action's input form, the runtime writes a signed authorization record, the guard picks it up on its next tick (or on SIGHUP via the socket), bakes or re-bakes the spend macaroon, and reports the new caps. Lowering caps and disabling sending remain one click in the admin UI (the safe direction is free). Nothing on the network can mint spend authority.

## 6. Protocol behavior

### 6.1 Lightning Address (LUD-06/16, NIP-57)

Wallet fetches `/.well-known/lnurlp/{name}` from `edge`: `callback`, `minSendable`/`maxSendable`, `metadata` (`text/plain`, `text/identifier`), `commentAllowed`, `allowsNostr: true`, `nostrPubkey` = that identity's zap-signing pubkey. All of this is derived from `identities/identities.json`; no secret involved. The callback validates amount and comment, and if a `nostr` zap request is present validates it per NIP-57 Appendix D (kind 9734, signature, single `p`, at most one `e`, amount tag matches, relays tag present) — pure computation. It then sends `{identity, amount_msat, description_hash, zap_request?}` to `core` over `edge-core.sock`. Core calls `AddInvoice` with the recv macaroon, records the pending zap keyed by payment hash, returns `pr` and a `verify` URL. On `SubscribeInvoices` settlement core builds the kind-9735 receipt, signs it with the identity's key, and publishes it to the relays named in the zap request plus the identity's configured relays plus the embedded relay. Invoices carry a custom record / memo prefix tagging the identity so the ledger and NWC `list_transactions` can be filtered per identity.

### 6.2 NIP-05

`/.well-known/nostr.json?name=` from `identities.json`: `names` (identity → the *user's* npub in hex, distinct from the service's zap-signing key) and no `relays` hint (decided 2026-10-21: the hint says where the user's own events live, which the embedded relay is not — it would steer clients to a relay that refuses the user's notes; wallet apps learn the NWC relay from the connection string, and Damus keeps it in the wallet settings rather than the relay list). Lowercase-only names, CORS `*`, cacheable. Bare-domain `_` name supported.

No `relays` hint is returned, and that was looked at again on 2026-11-19 after seeing that BOLT12 Pay returns one. It stays out: the usual path is that a client is already showing a profile and checks its NIP-05 name over HTTPS, at which point it has found the person's events and a relay hint tells it nothing; and this service's own relay is not where anyone's notes live, so the only honest hint would be a list the operator has to supply and keep current.

### 6.3 NWC (NIP-47)

Each identity can have many connections; each connection has a label, its own client keypair (secret shown once as URI/QR), a permission set from `{get_info, get_balance, make_invoice, lookup_invoice, list_transactions, pay_invoice}` (keysend and multi-pay deliberately out of v1), a budget (amount per rolling period) and a per-payment max, an optional expiry, and a `revoked_at` — revoked, never deleted, so audit lines keep their referent. The NWC **service key is per identity** (generated with the identity, encrypted at rest like the zap key): it is what a connection URI names, what signs that identity's kind-13194 info event and its 23195/23196/23197 events, and what the relay ACL and budget attribution key on, so two identities never share a wallet-service pubkey. Each identity's NWC runs on one relay — the embedded relay by default, or a per-identity override the operator sets (decided 2026-10-21) — which is what its connection strings name, where its 13194 info event goes, and where core reads 23194 requests and writes 23195/23196/23197; the per-identity relay list is for zap receipts only. Core keeps one subscription over the union of those relays, encrypts with NIP-44 (NIP-04 fallback for older clients, configurable), and publishes 23195 responses and `payment_received` / `payment_sent` notifications, each as kind 23197 under NIP-44 and kind 23196 under NIP-04. **Each identity is a virtual wallet (decided 2026-10-21).** Its balance is its own ledger: settled incoming (`amt_paid`, so overpayments count) plus operator adjustments, minus settled outgoing (amount + actual fee) and in-flight outgoing (amount + fee limit, released or settled when the payment resolves). A fresh identity starts at zero, like an LNbits wallet, and the operator credits or debits it from the admin UI; an adjustment is bookkeeping only — nothing moves on the node, the sum of identity balances is not reconciled against channel liquidity, and a credited identity can still fail at LND with `INSUFFICIENT_BALANCE`. Adjustments appear in `list_transactions` the way an LNbits top-up does — a settled incoming (credit) or outgoing (debit) entry with no invoice and a synthetic payment hash derived from the adjustment id — so a wallet's history sums to the balance it shows (decided 2026-10-21 after checking Damus against LNbits; the first draft hid them). `pay_invoice` checks the balance first (under the same lock as the connection budget, returning NIP-47 `INSUFFICIENT_BALANCE`), then the connection's per-payment max and period budget (`QUOTA_EXCEEDED`), and only then reaches the guard, whose caps remain the hard floor. `get_balance` returns the identity balance, full stop: an app always sees what is there even when its connection's budget makes part of it unspendable, and a negative position (operator debit) reads as zero. Nothing about the node's channel balance is ever reported. `pay_invoice` is refused outright while the guard latch is off, before any LND call.

### 6.4 The embedded relay

khatru (`fiatjaf.com/nostr/khatru`) embedded in `edge`, mounted at `/relay`, SQLite event store in `edge/`. It is a *purpose-built* relay, not an open one:

- Accepted kinds only: 13194 (NWC info, replaceable), 23194/23195/23196/23197 (NWC traffic), 9735 (zap receipts). Kinds 0 and 10002 were in the first draft and dropped 2026-10-21: nothing in the service publishes them and the relay is not a home for anyone's profile or notes. 1059 optionally later for DMs about payments.
- Author policy: 23194 only from client pubkeys in `identities/nwc-clients.json` (non-revoked) and only `p`-tagged to the service pubkey of the identity that client belongs to; 13194/23195/23196/23197 only from an identity's service pubkey; 9735 only from an identity's zap key. Everything else rejected with a reason.
- Ephemeral does not mean instant (found on the box 2026-11-10). Damus's wallet screen publishes its request and only then subscribes for the reply; core answers in milliseconds, so the reply reached no listener and Damus showed a blank wallet (in October the same reply took half a second and happened to arrive late enough). The relay now keeps kinds 23194 and 23195 in memory for 60 seconds, at most 2048 of them, and serves them to a subscription that names those kinds — which also covers the half-second in which core's own subscription restarts after an identity change. Nothing is written to disk, notifications are not kept, and core never looks back past its own start, so a request answered by a previous process is not run again. strfry does the same by default for five minutes.
- Retention follows NIP-01's kind ranges rather than a timer: all four 2319x kinds sit in the ephemeral range (20000–29999), so the relay never stores them and only fans them out to live subscriptions — which is why core keeps its 23194 subscription permanently open and why a response a client missed is gone by design. 13194 is replaceable (10000–19999): keep the latest per service pubkey. 9735 is stored, because a receipt whose external publishes all failed would otherwise exist nowhere (and `RetryReceipts` stops once one relay has it). khatru models all of this if the kinds are declared correctly.
- Abuse bounds for anonymous WebSocket clients, which the relay must accept because the pairing wallet is anonymous until it speaks: global cap on concurrent connections (e.g. 256) with LRU eviction of idle ones; per-connection cap on open subscriptions (8) and on messages per second; idle timeout (60 s without a frame); maximum event size by kind — 16 KiB for anything a stranger can send (an NWC request is a few hundred bytes, a receipt a few KiB), 96 KiB for the kinds only this service's wallet keys may publish (23195–23197; see the reply-size paragraph below) — but a WebSocket frame limit of 256 KiB (found on the box 2026-10-23: Damus sends its ordinary timeline REQs, follow list and all, to every relay in its pool including the wallet relay; with the frame limit at 16 KiB the socket closed on every connect and no response ever found a listener — the "mute: no one was listening" in core's log), tag-count and filter-complexity limits from khatru's `policies` package; REQ result cap (100 events) and a short query timeout; a kind-based rejection *before* signature verification so unaccepted kinds cost nothing. Per-IP limits keyed on the rightmost `X-Forwarded-For` (§4.2) as a second layer, never the only one.
- **`lookup_invoice` covers payments too (2026-11-12).** NIP-47 has one lookup for both directions, and a wallet asks it about a payment it has just sent. The first version searched only invoices this service had issued, so a sent payment was `NOT_FOUND`. It now searches the identity's invoices and its payments, by payment hash or by BOLT11 string (normalised: lower case, `lightning:` prefix dropped; the string search covers the same latest 500 of each that `list_transactions` reads), and returns pending and failed payments as well as settled ones. A self-payment within one identity has an invoice and a payment under the same hash: the connection that created the invoice is answered with the invoice, a connection that only paid with the payment. Records of another identity are `NOT_FOUND`, indistinguishable from a hash that does not exist.
- **Who a transaction was with (2026-11-11).** Checked against Damus's source after a self-zap showed "+33 from User" and "−33 to Unknown". Damus names a row from the kind-9734 zap request it finds in the transaction (`description` parsed as an event, else `metadata.nostr`): the request's `pubkey` for an incoming row, its first `p` tag for an outgoing one. Incoming rows already carried the request this service received on the LNURL callback. Outgoing rows carried nothing, because an invoice names a node and an amount, never a person, and the only source is the paying app, through NIP-47's optional `metadata` on `pay_invoice` (`metadata.nostr` for a zap), which `pay_invoice` was not reading. It now keeps `metadata` (any JSON object, at most 8 KiB, compacted, otherwise dropped without failing the payment), falls back to a `description` that parses as a kind-9734 event, stores it on the payment and returns it as `metadata` in `list_transactions` and `payment_sent`. It is the app's claim and is not verified against the invoice's description hash — an app's re-encoding of the event need not hash the same — and it is visible only to connections of the same identity. For a self-payment with no metadata the row falls back, at read time, to the zap request on this node's own invoice record (public anyway: it is in the zap receipt), which also covers self-zaps made before this change. Payments made earlier to other nodes stay "Unknown"; the information was never stored. **Damus itself does not send it (found on the node the same day):** an outgoing zap to another node still showed "Unknown". Damus has the code to build such a request (`WalletConnect.Request.payZapRequest` fills both `metadata.nostr` and `description`), but its zap button calls `nwcPay` without the zap request and `nwcPay` passes `zap_request: nil` to `WalletConnect.pay` whatever it is given (source as of 2026-09-09), so `pay_invoice` arrives with the invoice alone. With that app the recipient of an outgoing zap is unknowable to any NWC wallet service unless it finds the zap request elsewhere — the kind-9735 receipt carries it in its `description` tag, and `sha256` of that must equal the invoice's description hash, so a receipt lookup would be verifiable; not built. Each `pay_invoice` now logs whether the app attached metadata (`app_sent_metadata`, `app_sent_description`, `recipient_known`), never its content. Private zaps: Damus signs the request with a throwaway key and puts the real request, encrypted to the recipient, in an `anon` tag. This service passes the request through untouched, so the wallet row shows the throwaway key; only the recipient's own Nostr key can open the `anon` tag (which is how Damus's notifications still name the sender), and this service never holds that key.
- **How a settlement is learned, and the safety net under it (2026-11-19).** Core follows LND's invoice stream (`SubscribeInvoices`, resumed from the last settle index, with every open invoice looked up again on each reconnect), so a payment is known within milliseconds and the receipt and the NWC notification go out at once. Comparing with BOLT12 Pay, which has no stream and instead polls LND (each pending zap every one to fifteen seconds, and a full sync before every `lookup_invoice`), showed the one case where polling is the more robust: a stream that stops delivering without ending. Nothing here would have noticed; a paid invoice would have stayed "pending" in every wallet, with no receipt and no notification, until the next reconnect. It was never observed, but nothing ruled it out. Two additions close it without giving up the stream. Every two minutes core looks up its open invoices in LND directly (the newest 500; unpaid ones expire, so there are normally a handful) and settles what it finds; a settlement found that way which is more than 30 seconds old is taken as proof the stream is not delivering, and the stream is closed and reopened. And when a wallet asks about an invoice that is still open here — NWC `lookup_invoice`, or LUD-21 `verify`, which a payer's wallet polls right after paying — core asks LND about that one invoice before answering. `verify` is a public endpoint, so that lookup is limited to about one every three seconds per invoice and five a second overall; over the limit the answer comes from the ledger as before. A settlement is applied by one atomic transition whichever path sees it first, so the stream, the periodic check and a lookup racing each other still settle an invoice, send its receipt and notify exactly once.
- **A reply is one event, so replies are sized to fit (2026-11-10).** Found on the box: Damus showed a balance and an empty history, because the `list_transactions` reply — it asks for the latest 50, once, over NIP-04 — carried a dozen zaps with their kind-9734 requests, ran past the 16 KiB event limit, and the relay refused its own service's answer (`invalid: event too large`); nothing told the wallet. Two changes. The relay's limit for service-authored kinds is 96 KiB, as above. And core never builds a reply that will not fit: `list_transactions` has a budget of 60,000 bytes of JSON on the embedded relay and 40,000 on an operator-chosen relay (public relays commonly stop at 64 KiB per event; NIP-44 pads and base64 adds a third, so those become about 87 and 55 KiB of content, and NIP-44 cannot encrypt more than 65,535 bytes at all). A page over budget gives up the least useful data first: the BOLT11 string of entries no longer payable, then `metadata` (where the zap request lives) from the oldest entries one at a time so the newest still name their zapper, then the oldest entries themselves. Every other reply that somehow does not fit — or cannot be encrypted — is replaced by an `INTERNAL` error so a wallet is never left waiting for an event that will not arrive. LNbits, for comparison, sends the page whole with every BOLT11 and empty metadata (the zap request rides in `description`), and its relay limits storage per account rather than the size of one event. The in-memory buffer of recent requests and replies is bounded in bytes (32 MiB) as well as in events now that a reply can be large.
- **Checked against the specifications (2026-11-12).** NIP-47 was slimmed on 2026-11-07 to a core of five methods (`pay_invoice`, `make_invoice`, `lookup_invoice`, `get_balance`, `get_info`); everything else moved to numbered optional specs at github.com/nostr-wallet-connect/nwc, which a wallet service names in an `extensions` tag on its info event and an `extensions` array in `get_info`. Read against NIP-47 at `b587c61` and the extension specs at `2e2070d`. This service implements the core plus **02** (notifications), **05** (`list_transactions`) and **06** (metadata conventions), and says so in both places. What the pass changed:
  - *The two notification kinds were the wrong way round.* NWC-02 puts NIP-44 notifications on kind 23197 and NIP-04 ones on 23196; this service had them swapped, so an app listening on the kind for its encryption got ciphertext it could not read. Nobody noticed because Damus does not subscribe to notifications at all. An e2e test now decrypts each kind with its own scheme.
  - *An unknown `encryption` tag is answered, not dropped.* A request tagged with anything but `nip44_v2` or `nip04` gets `UNSUPPORTED_ENCRYPTION`, encrypted with NIP-44 (the scheme the info event lists first). A request with no tag is NIP-04, as the spec says.
  - *Metadata is at most 4096 characters, or it is dropped* (NWC-06; the limit here was 8 KiB). That holds for what an app sends with `pay_invoice` and `make_invoice` and for what this service assembles: if a zap request pushes a transaction's metadata past the limit, the zap request goes and the comment and payer data stay.
  - *`make_invoice` keeps the app's `metadata`* and returns it from `make_invoice`, `lookup_invoice` and `list_transactions`, under this service's own keys (`comment`, `nostr`, `payer_data`) where they collide. It was accepted and thrown away before.
  - *An invoice that ran out is `expired`.* It was reported as `failed`, which the spec keeps for payments. A canceled invoice is `expired` too: NIP-47 has no `canceled` for invoices (NWC-09 does, for `lookup_payment`).
  - *`list_transactions` returns `total_count`* — how many transactions match the filters before paging — when it is exact, and leaves it out once any of the three sources is at its 500-row read limit.
  - *`unpaid: true` adds unpaid invoices; it takes nothing away.* Operator adjustments were left out of the list whenever `unpaid` was set, from reading it as a filter. Found by the conformance test, confirmed against LNbits (`complete=True, pending=unpaid`).

  Deliberately not implemented, and so not advertised: **03** hold invoices and **04** keysend (both widen what a connection can make the node do); **09** `lookup_payment` (its `transaction_id` and `MULTIPLE_MATCHES` would be the right answer to the self-pay case `lookup_invoice` settles by connection, worth doing when an app asks for it); **13** `get_budget` (draft; it reports a budget that resets at fixed times, where a connection's budget here is a rolling window, so an honest answer needs either a `renews_at` that is only an estimate or a change to how budgets reset); **07** and **08** connection deep links; **12** BOLT12 and **321**, which wait on §8. `multi_pay_invoice` and `multi_pay_keysend`, left out of v1 above, are no longer in NIP-47 or any of the extension specs, so there is nothing to implement. Two things in NIP-47 this service does on purpose and an operator should know: `get_info` gives every connected app the node's alias and public key, as the method is defined; and the spec says a wallet service SHOULD NOT store the secret it generates for a client — this one shows it once and keeps only the public key, which is why a lost connection string means a new connection.
- NIP-40 (added 2026-10-21, from comparing with LNbits's nwcprovider): the relay rejects any event whose `expiration` tag is already past, and core's NWC handler checks the tag again before dispatching, so a payment request a wallet gave up on is never executed late through a relay that doesn't enforce it. The relay's own stored events expire via khatru's expiration manager.
- Optional NIP-42 AUTH for REQs on 23194/23195 so third parties cannot enumerate connection activity (NWC payloads are encrypted anyway, so this is metadata hygiene, off by default because not every wallet implements AUTH).
- NIP-11 document names the operator's contact and the supported NIPs. The relay is advertised nowhere but in NWC connection strings.

Why embed rather than depend on the `nostr-rs-relay` StartOS package: same domain and certificate, no second service to expose, a policy that is part of this package's security model rather than a general relay's configuration, and zero secrets in the process that holds it.

### 6.5 Self-pay: a node cannot route to itself

Found on the first on-node test (2026-10-21): Damus produced a zap invoice from this service and Zeus, on the same LND, reported "no route" — Lightning has no path from a node to itself, so no invoice this node issues can ever be paid by this node over the network. LNbits's "self-pay" flag is the equivalent problem solved inside LNbits: a payment *through LNbits* for an invoice LNbits issued moves balance between its wallets and never touches Lightning. The same here, and only here: when NWC `pay_invoice` arrives for a payment hash in our own invoice ledger (identity A paying identity B, both through this service) and the operator's self-pay setting is on, core settles it internally — balance and budget checks as for a real payment, `LookupInvoice` for the real preimage (LND returns it for its own invoices in any state), `CancelInvoice` on LND *first* so the invoice can never also be paid over the network (and so a race with an external settlement fails safe, since cancelling a settled invoice errors), then the payer's payment row (settled, no fee, `internal: true`) and the payee's settlement through the same path LND's subscription uses (receipt, notification). The guard is not involved: nothing leaves the node. With self-pay off the request is refused up front with a message naming the setting, rather than timing out in LND. A wallet paying through LND directly (Zeus on the same node) is unaffected either way; it will always get "no route", and the docs say so.

Lightning settings — route hints (`private`), self-pay, invoice expiry, routing fee limit — are a card on the Admin UI dashboard stored in core's database and read on each `CreateInvoice`/`PayInvoice` (no restart); the environment defaults apply only until the operator first saves.

**Routing fee limit (2026-11-10).** What core passes to LND as `fee_limit_msat` is `max(amount × percentage, floor)`, both operator settings: 0–10 % and 0–1000 sats, not both zero, default 1 % and 10 sats. The first version hard-coded 1 % with a 1-sat floor, and on the node 1- and 3-sat zaps failed with `FAILURE_REASON_NO_ROUTE` while Zeus paid the same invoices: most nodes charge a base fee near 1 sat per hop regardless of amount, so a 1-sat ceiling only fits a direct channel or a single cheap hop. For comparison, LNbits reserves `max(2 sats, 1 %)`, and LND's own default where a caller names no limit (`lncli`, the legacy send RPCs) is 100 % of the amount up to 1000 sats — "to accommodate for base fees", in its source — and 5 % above. The limit is the in-flight hold on the identity's balance (§6.3) and is part of what the guard prices against both caps (§5.2), so raising it makes small payments need more headroom — a 1-sat zap needs 11 sats available at the defaults — but costs nothing: on settlement only the fee LND reports is booked. The bounds exist because the setting lives in the Admin UI, not behind the authorization ceremony: the highest it can be set is 10 % of the amount or 1000 sats, whichever is larger, and the guard's caps still bound amount plus limit. Settings saved before the fields existed read as zero and get the defaults.

## 7. Data model (core SQLite)

`identity(id, name, display_name, user_npub_hex, nip05_enabled, zap_pubkey, zap_key_enc, min_msat, max_msat, comment_len, relays_json, created_at)`; `nwc_connection(id, identity_id, label, client_pubkey, permissions_json, budget_msat, budget_period, max_payment_msat, expires_at, revoked_at, created_at)`; `invoice(payment_hash, identity_id, amount_msat, description_hash, zap_request_json, state, settled_at, preimage_enc)`; `payment(payment_hash, connection_id, amount_msat, fee_msat, state, created_at)`; `ledger(id, identity_id, kind, msat, ref, created_at)` append-only. `identity` also carries `nwc_pubkey, nwc_key_enc` (§6.3). The admin UI never displays an nsec.

### 7.1 Keys at rest, backup and what rotates

Three kinds of key live in `core/`: the per-identity zap-signing keys, the per-identity NWC service keys, and one **master key** (`core/master.key`, 0600, uid `core`, generated by the package JS at install) that encrypts the first two in SQLite. None of them is tied to LND. Being honest about what this buys: with the master key in the same volume, encryption at rest does not protect against a compromise of `core` itself; it protects against key material leaking through exports, logs, debug dumps and future admin-UI splits, and it is what makes rotation a re-encryption rather than a migration. StartOS backups are encrypted with the server's master password, so `core/master.key` is included in the backup on purpose: a restore, including onto a replacement LND node, brings every identity and every NWC pairing back working, and only the macaroons need `rebake-credentials`.

What rotates, and what it costs: the **master key** rotates via the `rotate-master-key` action (re-encrypt in place, no externally visible change; do it after any suspected read of the volume). A **zap-signing key** rotates per identity from the admin UI; the identity's `nostrPubkey` in the LNURL document changes, old receipts stay valid, nothing to re-pair. An **NWC service key** rotates per identity only on suspected compromise, because every connection URI for that identity names it: all of that identity's connections are revoked and must be re-paired, and the identity's 13194 info event is republished. Connection *client* keys are not rotated, they are revoked and replaced. A restore from a backup taken before a rotation reverts to the pre-rotation keys, which is the normal backup semantics and should be said in the docs.

## 8. Milestone 3: BOLT12 via LNDK

A fourth subcontainer running `lndk` with its own guard-baked macaroon (§5.1), gRPC on loopback `:7000` with LNDK's own TLS + macaroon, reachable only from core. Core creates one offer per identity (`create-offer`) and shows the BIP-353 `TXT` record (`name.user._bitcoin-payment.domain`) the operator must publish in DNS — the package cannot write external DNS and should not grow a Cloudflare integration in v1. LNURL `/.well-known/lnurlp` can advertise the offer where wallets look for it. Keep milestone 3 receive-only unless a `SendToRouteV2` pricer is added to the guard's middleware logic (§5.1): the middleware already sees the call, it just cannot price it. `lnd-startos` ≥ 0.21 advertises onion messages natively, so no LND reconfiguration is needed.

**Do offers survive a restart? Checked against LNDK's source (2026-11-11, master at `e0b2344`, 2026-04-14; latest tag v0.3.0, 2025-09-29).** A June 2026 survey said LNDK "generates a new key on each restart (preventing persistent offers)". That was true once and is not now.

- *The key is stable.* Since `9fccf89` (2025-05-26, in v0.3.0) LNDK derives the secret behind its offers (`ExpandedKey`) by asking LND to Schnorr-sign a fixed message with a fixed key locator (family 4, index 425) and hashing the signature; the comment calls this "stateless … restart-proof". LND's `SignMessageSchnorr` calls btcd's `schnorr.Sign` with no options, which uses RFC 6979 deterministic nonces, so the same wallet always yields the same key. An offer keeps working across LNDK and LND restarts, and across reinstalling LNDK, for as long as the LND wallet is the same. It needs `signrpc` and a macaroon that may sign messages.
- *LNDK keeps no list of offers.* Its API is `CreateOffer`, `PayOffer`, `GetInvoice`, `DecodeInvoice`, `PayInvoice`; each `CreateOffer` picks a fresh nonce, so asking twice gives two different (both valid) offers and there is nothing to list. Core must create an identity's offer once and store the string itself; that string is what goes in DNS.
- *What can break a stored offer is its paths, not its key.* At creation LNDK puts up to three blinded message paths in the offer, each entering through a peer with which the node has an **active public** channel and which supports onion messages. If those channels later close, the offer stops being reachable though it is still "valid", and nothing announces it. Core should record the entry peers when it creates an offer, compare them with the open channels periodically, and tell the operator in the Admin UI when an offer needs regenerating — which means a new DNS record, by hand.
- *A node with only unannounced channels gets a degenerate offer.* With no public channel LNDK falls back to a one-hop path that names the node itself as the entry point. A payer then has to reach this node directly, and a node with no public channel has no node announcement in the gossip graph for a payer to find it by. To be tested before any of milestone 3 is built: whether a payer (Phoenix) can pay such an offer at all, and whether LND will build the blinded *payment* paths (`AddInvoice` with `is_blinded`) through unannounced channels.
- *LNDK, not core, creates the invoice.* On an invoice request LNDK calls LND `AddInvoice` itself (memo = the offer's description, 24-hour expiry, blinded). Core never sees the request; it sees a settled invoice it did not create. Crediting the right identity therefore rests on the memo, so each identity's offer needs a description unique to it, and core's invoice watcher needs a rule for invoices it has no record of. LNDK's macaroon needs `AddInvoice` among others, which the guard would bake.
- *BIP-353 is still on LNDK's to-do list (v0.4.0).* Not needed here: this package only shows the `TXT` record for the operator to add by hand, and resolving `name@domain` is the payer's wallet's job.

**Is LNDK necessary, and can it even run here? (2026-11-11, from LND master at `0123a54` and LNDK master at `e0b2344`.)** Prompted by the question of whether to roll our own BOLT12 rather than depend on LNDK. Three findings change milestone 3.

- *LNDK as written very likely cannot receive onion messages from the StartOS LND.* LNDK gets onion messages by subscribing to LND's custom-message stream for type 513, which only works when LND is started with `protocol.custom-message=513` (plus `custom-nodeann=39`, `custom-init=39`). LND 0.21 handles onion messages itself; `custom-init`/`custom-nodeann=39` now abort startup ("feature bit: 39 already set"), and lnd-startos forces all three keys to undefined so an operator cannot set them. Without the override LND parses 513 natively and never hands it to custom-message subscribers. The sentence above that "no LND reconfiguration is needed" missed that LNDK needs the override to *receive*. Not tested; this is from reading both code bases.
- *LND 0.21 exposes what a BOLT12 receiver needs.* `SubscribeOnionMessages` (peer, path key, onion, reply path, encrypted recipient data, and the TLVs LND does not define as `custom_records`) and `SendOnionMessage` are in the 0.21 API (already in this repo's vendored `lightning.proto`). The payment half is LND's own blinded invoices (`AddInvoice` with `is_blinded`, which built three paths through this node's single unannounced channel on 2026-11-11); LNDK itself only copies those paths into the BOLT12 invoice.
- *LND is building BOLT12 natively.* The unreleased 0.22 notes list a `bolt12/` codec package (offer, invoice request, invoice, invoice error, checksumless bech32, Merkle and BIP-340 signing, spec test vectors, fuzzing), an `offers` SQL store, and an invoice-request handler behind an experimental `protocol.bolt12-offers` flag that needs a `dev` build and native SQL; "the node does not route invoice requests to the handler yet". No offers RPC is in `lightning.proto` yet.

*What rolling our own (receive only) would take, in Go, in this package:* the BOLT12 TLV codecs and validation; Merkle root and BIP-340 signature with a per-identity offer key held sealed in core like the zap key (an offer may name any `offer_issuer_id`, so no LND signing is needed); blinded message path construction for `offer_paths`, with a `path_id` to bind requests to the offer; reading invoice requests from `SubscribeOnionMessages`; building the invoice from `AddInvoice(is_blinded)` + `DecodePayReq`; and — the hard part — sending the reply: constructing the Sphinx onion message and finding a route of onion-message-capable nodes to the reply path's introduction node, since LND 0.21 drops onion messages from peers with no open channel, so connecting straight to the introduction node (what LNDK does) is not reliable. Permissions: `SubscribeOnionMessages`, `SendOnionMessage`, graph reads, `AddInvoice`, `DecodePayReq`, and `signrpc.DeriveSharedKey` if `path_id` is checked. None can move funds; the failure modes are offers that do not work, invoice-request floods creating LND invoices (needs its own rate limit), and privacy mistakes that tie an offer to the node. It would be the largest and most protocol-sensitive code in the project, and its real cost is interop testing against CLN, LDK and Eclair payers.

*Options, least risk first:* (1) wait for LND's native support and integrate it (create one offer per identity, watch settled invoices — no new crypto, no new daemon, no new permissions beyond an offers call); (2) build receive-only ourselves on LND 0.21's onion RPCs, after a spike that proves two things on a real node: what `SubscribeOnionMessages` delivers for a final-hop invoice request on 0.21.6, and that a wallet pays a BOLT12 invoice assembled from LND's blinded paths; (3) LNDK, only if it moves to LND's native onion RPCs. Either way the node needs an entry peer that relays onion messages (§ above), so the public-channel question is independent of this choice. **Decided 2026-11-12: wait for LND's native BOLT12 (option 1).** Milestone 3 becomes "integrate LND's offers once they ship in a release build"; nothing is built on LNDK and no BOLT12 code is written here in the meantime.

*Where LND's own BOLT12 stands, and the plan (2026-11-13).* Read on master at `895118a`. The roadmap (lightningnetwork/lnd#10736) has six milestones — codec, receiver, sender, multi-hop, PayOffer, RPC parity — and only the codec is complete. The receiver can create an offer and answer an invoice request with a signed invoice, but cannot settle the payment: the handler keeps no invoice row and no preimage ("a later change adds the state that a payment needs to settle the invoice"). Offers must name the node key (offers behind blinded paths are refused), onion messages are accepted only from a peer with an open channel, and a reply goes out only when the payer's reply path starts at a direct peer. All of it is compiled out of release builds: the `protocol.bolt12-offers` flag exists only under the `dev` build tag, the only way to create an offer is `CreateOffer` on the dev RPC sub-server, and the `offers` table is a development migration that only `test_native_sql` builds apply. The v0.22.0 milestone was due 2026-11-15 at 28 % complete with no release candidate; past releases took six to seven weeks from rc1, so early 2027 at the soonest, and unless the migration is promoted first that release will carry the code without a way to reach it.

lnd-startos is not the obstacle on the database side: "native SQL" is a schema mode, not a different database, and the package already starts LND with `--db.use-native-sql` on SQLite; onion messages and route blinding are on by default. The obstacle is that it ships the official release image, which has neither build tag. A custom dev build on the real node was considered and rejected: master is a one-way upgrade to unreleased 0.22, and the development migration occupies a version number (20 today, already renumbered once) that a release is likely to give to something else, on a node that holds funds — for a flow that cannot complete.

Plan: when LND's receiver can settle a payment, prove the integration in **regtest** on a workstation (bitcoind and two LND dev builds with a channel between them, this service's binaries pointed at one), not on the box. In the package, BOLT12 is gated on what LND actually offers: the guard probes for the offer RPC and BOLT12 stays off when LND answers "unimplemented" — no version check. Anything written against the dev RPC is throwaway, since the roadmap's last milestone moves offers onto the ordinary invoice and payment RPCs. What to watch for upstream: the offers migration moving out of `sqldb/migrations_dev.go` into the main list, and the flag losing its `dev` tag.

## 9. Build base and language (decided 2026-10-21: Go, written fresh)

**Build base, as it turned out.** The plan above was "fork brollyzapper for parts". The implementation did not: the guard, NWC, LNURL and zap code were written fresh, and the LND transport is REST rather than gRPC, so there was no generated protobuf code to inherit either. What was taken from brollyzapper is the *design* — the guard/server split, URI-scoped permissions, `time-before` renewal, the custom-caveat middleware for milestone 2, revoke-don't-delete — not its code. The reasons not to wrap bolt12-pay (§2) and not to fork brollyzapper whole (§3) stand; the "vendor its packages" step simply proved unnecessary once the pieces were small enough to write with tests (guard ≈ 300 lines, the whole service ≈ 3.5k). The one piece of brollyzapper worth revisiting later is its regtest harness (bitcoind + two LNDs + a relay) as a model for integration CI beyond the fake-LND e2e test.

**Language: Go, deliberately, over .NET, Rust and Node.** The maintainer's strongest language is C#/.NET; the choice was made knowing that, for the following reasons, and with the alternatives weighed honestly.

*Go* is what the service is written in. What it actually depends on is two libraries — `go-nostr` (keys, signing, NIP-04/44, relay pool) and `khatru` (the embeddable relay with policy hooks) — plus the deployment shape: `CGO_ENABLED=0` static binaries, trivial `GOARCH=arm64` cross-builds, three processes idling at 10–20 MB each, and a standard library that covers HTTP, TLS, JSON and the `SO_PEERCRED` syscall the socket model rests on. It is the fastest language for a C# developer to become a confident *reader* of, which is the property that matters for a sole maintainer auditing a credential broker, and it is the language of LND, Alby Hub and brollyzapper if community contributors ever arrive. Known costs: `if err != nil` verbosity, nil, and khatru having moved to `fiatjaf.com/nostr/khatru`, so the relay dependency gets migrated at some point (a good first Go change).

*Rust* has the better ecosystem fit and was the serious alternative: rust-nostr's `nostr-sdk` with first-class NIP-47 types, `nostr-relay-builder` as a maintained khatru equivalent, a `macaroon` crate, `peer_cred()` built into tokio, pure-Rust `redb`, the smallest binaries, and LNDK itself is Rust, so milestone 3 would share a toolchain. It was not chosen because the safety it adds over Go is marginal for this workload (Go is memory-safe; the risks here are protocol and logic errors) while its learning curve is paid at every edit, which is the wrong trade for a sole maintainer learning as they go. Milestone 3 is the point to revisit it.

*Node/TypeScript* already lives in the repo as the StartOS package layer and stays exactly there. For the service it is disqualified by the guard: Node cannot read a unix socket peer's uid without a native addon, which removes the `SO_PEERCRED` check, and a credential broker carrying a few hundred transitive npm packages is the wrong shape for the one process that reads `admin.macaroon`. The edge alone would have been fine in it (nostr-tools holds the reference NIP-44), which is not a reason to split the service across two runtimes.

*.NET* was ruled out by the maintainer: learning Go for the transferable benefit was preferred over comfort. The design keeps the option open anyway: the three processes speak only length-prefixed JSON over unix sockets, so any one of them could be rewritten in another language without touching the others.

## 12. Roadmap

**Milestone 1 — receive (done, unreleased).** Everything in §0.

**Milestone 2 — sending (implemented 2026-10-21, awaiting a real-node test).** The point of this milestone is that money can leave the node only through a credential the guard baked, capped inside LND's request path, after a ceremony that happened in StartOS rather than over HTTP. In order:

1. *Guard: the middleware, over gRPC (decided 2026-10-21).* `RegisterRPCMiddleware` is a bidirectional stream, and the interceptor delivers each intercepted call as an `RPCMessage` whose payload is the serialized protobuf of the request (`SendPaymentRequest`), so the guard needs generated `lnrpc` types to price anything regardless of transport; given that, the stream itself belongs on gRPC rather than hand-rolled over the REST proxy's WebSocket. Get the stubs the way brollyzapper does, not by importing the LND module (which drags in btcd, btcwallet and a few hundred transitive modules): copy `lightning.proto`, `router.proto` and `stateservice.proto` into the repo pinned to the supported LND version, generate with `buf`, commit the `.pb.go` files. New dependencies are only `google.golang.org/grpc` and `google.golang.org/protobuf`. The guard becomes the one gRPC user (it can bake over gRPC too); core keeps the REST client. The middleware registers under `lightning-identity-guard`, reconnects forever, and reports `middleware_registered` in its status; while it is down the spend credential is dead, never unrestricted.
2. *Guard: the spend credential.* `SendPaymentV2`, `TrackPaymentV2`, `DecodePayReq` with `time-before` and `lnd-custom lightning-identity-guard <nonce>`; renewed on the same hourly tick; baked only while the latch is on.
3. *Guard: the pricer and the caps.* For `SendPaymentV2`, decode the bolt11 (or the `amt_msat` for amountless invoices) and check per-payment and rolling 24-hour caps against `guard/state.json`; reject by replacing the request. Any other intercepted method without a pricer and not on the read-only allow-list is rejected (fail closed).
4. *Package: the ceremony.* `enable-sending` and `raise-caps` actions write a signed authorization into `guard/`, which only the guard mounts; `disable-sending` and lowering caps are one click in the admin UI. The guard reports the caps it enforces; the admin UI shows them.
5. *Core: paying.* NWC `pay_invoice` (and later `multi_pay_invoice`) through the spend credential; a `payment` ledger; per-connection budgets and `max_payment_msat` as the soft layer under the guard's hard caps; `get_balance` as remaining budget (superseded by 2b); `list_transactions` with outgoing entries; `payment_sent` notifications; `pay_invoice` advertised in `get_info` and the 13194 event only while sending is on.
6. *Tests.* The fake LND grows `SendPaymentV2`/`TrackPaymentV2` and a middleware stream so `internal/e2e` can prove: no spend credential without the latch, a payment over the per-payment cap refused by the guard not by core, the 24-hour window, and that a core which ignores its own budget still cannot exceed the guard.

Scope guard for milestone 2: no keysend, no BOLT12 paying, no LNDK.

**Milestone 2b — identity balances (implemented 2026-10-21).** Identities become virtual wallets (§6.3): a ledger balance per identity that gates `pay_invoice` and is what `get_balance` reports; operator credits and debits from the admin UI; `ChannelBalance` dropped from the receive credential. The guard is untouched. `sending_test.go` proves an empty identity is refused with `INSUFFICIENT_BALANCE` before the guard sees anything, that a credit makes the same payment succeed and the balance drops by amount plus the actual fee, that a budgeted connection still sees the whole balance, and that a debit below the need is refused again.

**Lightning settings and self-pay (done 2026-10-21, same day as the first on-node test).** §6.5. The settings went to the Admin UI rather than a StartOS action because they are application settings with no security weight, must not restart the service, and the UI already owns per-identity settings; actions stay for what must be out of band (sending authorization) or what the OS owns (domain, password). Also from that test session: every Nostr event in or out is logged at info with kind, id, pubkey and `p`/`e` tags, every NWC request with method and outcome, every relay accept/reject with the reason — the trace that made the zap and NWC paths debuggable from the service log.

**Milestone 3 — BOLT12 receive, on LND's native support (re-scoped 2026-11-12; was "via LNDK").** §8: LNDK cannot receive onion messages from LND 0.21 as packaged on StartOS, and LND is building offers itself (unreleased 0.22, experimental). Wait for that to reach a release build, then: one offer per identity, the BIP-353 record shown for the operator to publish by hand, settled offer invoices credited to the identity. Needs an entry peer that relays onion messages (a public channel) on the operator's node. Paying offers is its own, later decision.

## 13. Security review after the LNbits incident (2026-11-09)

**What happened to LNbits.** On 2026-11-08 LNbits told every operator to shut down after funds were drained from several instances (one operator lost about 2.29M sats over five hours); the first warning named the Paywall extension. No advisory had been published a day later, so this is read from the fixes, which are public. Paywall's file download fetched a URL supplied by whoever created the paywall with `urllib.request.urlopen` — which opens `file://` paths and loopback addresses as readily as public ones — and until then any visitor could create an account. The patches (Paywall `d8abb84`; core `7a176c5`, `fc5e0b6`, `b21eb6e`, shipped as 1.7.0rc2) put every user-controlled outbound request behind one validating client, refuse requests that loop back to the instance itself, validate Nostr relay URLs before connecting, turn public registration off by default, and stop a service fee being credited for a payment that had not succeeded. Three classes, then: a server-side fetch of an attacker's URL, an open front door, and money booked on an outcome that was not final.

**What that looked like here.** The front door is not open: identities and wallet connections are created only in the password-protected Admin UI, and nothing in the service reads a file or URL named by a user. The other two classes were present, and a review prompted by them found five things. All are fixed, each with a test that fails without the fix.

1. *A payment was booked as failed when the wait ran out, not when LND said so.* `PayInvoice` treated every error from `SendPaymentV2` — including its own 75-second timeout — as a failure and released the identity's balance; a reconciler then failed anything pending for two hours. A recipient who holds the HTLC (a hold invoice) keeps the payment in flight past both, and settles afterwards: the identity has its balance back and the node has paid. Now a payment leaves "pending" only on LND's verdict: a terminal status on the stream, or `TrackPaymentV2` (already one of the spend credential's three methods) saying succeeded, failed, or never started. Anything else stays pending and keeps holding the balance for as long as it takes; there is no timeout after which failure is assumed. The wallet is answered "still in flight" rather than "failed", and a `payment_sent` notification follows if it settles. A payment LND refused because the node already paid that invoice by other means is recognised by its creation time and is not debited to the identity.
2. *The guard released its reservation on any error from the stream.* LND reports an error to the middleware when the caller hangs up, which is exactly what happens in (1); the hard 24-hour cap could be walked past with hold invoices the same way. The guard now treats an error as "unsure" and asks LND (admin macaroon, over its own connection) what became of the payment; only never-started or failed releases, succeeded commits, in flight stays reserved. Reservations are also written to `guard/state.json`, so a guard restart cannot forget money in flight, and a reservation that cannot be written down is refused.
3. *The guard's pricing arithmetic could wrap.* `amount + fee_limit` was unchecked `int64`; a fee limit near the maximum made the total negative, which passed both caps and could drive the 24-hour ledger below zero. Every figure in the request is now range-checked (non-negative, at most 21M BTC in msat, sat and msat forms mutually exclusive, no amount on an invoice that has one) before anything is added.
4. *Core dialled relay URLs supplied by strangers.* A zap request names the relays its receipt goes to, and core connected to them when the invoice settled: for the price of a 1-sat zap, anyone could make core send requests to loopback, the StartOS bridge or the LAN — the same class as the LNbits bug, though blind (nothing is returned to the sender) and limited to a WebSocket handshake. Relay connections now go through a dialer that refuses any address that is not public, checked on the resolved address at connect time so redirects and DNS that resolves inward are covered; relays the operator configured (the embedded relay, an identity's receipt relays or NWC relay) are exempt. A zap request's relays are also cleaned and capped at 16.
5. *Smaller.* The invoice from a wallet app went into LND's REST path unescaped (now validated as bech32 and escaped; payment hashes must be hex) — not shown to be exploitable, since the credentials involved permit almost nothing, but it is the same "user string becomes a request" shape. A retried payment left a second index entry and was counted twice against the identity's balance and budget. Invoice state changes are now compare-and-set in one transaction, so a cancellation arriving late cannot undo a self-payment's settlement.

**What the design already bounded.** With (1) alone, an identity holder could spend more than their balance, but only up to the guard's caps — the reason the caps live in a separate process. With (2) and (3) those caps had holes, so the two layers failed in the same direction at once; that is the lesson worth keeping. The seed, the admin macaroon and the process holding them were never reachable by any of this.

**Not verified here.** Everything above is proven against the fake LND in `internal/e2e`. Two behaviours of real LND are assumed and want checking on the node: that `GET /v2/router/track/{payment_hash}` takes the hash base64-encoded and answers 404/NOT_FOUND for an unknown one, and that the middleware receives an `is_error` response when a `SendPaymentV2` caller disconnects. If either differs the result is conservative (payments stay pending, reservations age into "spent"), not unsafe.

## 14. LND's `public` credential tiers (2026-11-10)

lnd-startos 0.21.6-beta:2 and :3 (2026-11-08) added a second volume, `public`, that an `export-credentials` oneshot rewrites on every start once the wallet is unlocked: `payments/payments.macaroon` (baked: channel balance, create/look up/subscribe/cancel/settle invoices and hold invoices, `SendPaymentV2`, `TrackPaymentV2`), `readonly/readonly.macaroon`, and `admin/admin.macaroon`, each beside a copy of `tls.cert`. Its README now says dependents mount a tier of `public`, never `main` — the hazard §2.2 describes, closed on LND's side.

This package follows: the guard mounts `public`, subpath `admin`, read-only, in place of `main`'s macaroon directory, and the dependency floor is 0.21.6-beta:3. LND's `main` volume is no longer mounted anywhere here, not even a subpath of it. Nothing else changes: the exported macaroon is root-owned and not world-readable, so the guard still starts as root, reads it once and drops privileges (§10.2); a rotated root key reaches the tier on LND's next start, and the guard already exits and re-reads when LND refuses its copy.

Why `admin` and not a narrower tier: the guard's whole job is to turn the admin macaroon into narrower ones. It needs `BakeMacaroon` and `RegisterRPCMiddleware`, which neither `payments` nor `readonly` grant. And `payments`, handed to core directly, would be a step backwards — it carries `SendPaymentV2` with no caveat, so no middleware and no caps; what the guard bakes for core is narrower in every respect (four invoice methods to receive; three methods plus the custom caveat to send). The tiers are a good default for a package that trusts its own process; this one is built not to.

Depending on current lnd-startos also means building against start-sdk 4.0.0 (LND moved on 2026-11-05 and its source no longer type-checks under 3.0.6). For this package that was a version bump and a refreshed lockfile; no source changes. It moved again to start-sdk 4.1.0 on 2026-11-17 for action file uploads (the Upload Site action), which raises the floor to StartOS 0.4.2; again a version bump with no changes to existing source.
